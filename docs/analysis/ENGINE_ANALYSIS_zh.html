① 这是个什么项目？

pkmn/engine 是一个宝可梦对战模拟器的底层引擎。 它不是一个完整的游戏——不渲染画面、不连服、不管账号。它只做一件事：

吃下"两方训练家的选择" → 推进战斗状态 → 输出胜负与日志。
要做到与原版 GB 卡带和 Pokémon Showdown 逐帧一致，并且比 Showdown 快 1000 倍以上。

核心实现

Zig (src/lib) → 编译为 libpkmn.so / WASM

驱动代码

TypeScript (src/pkg) → npm 包 @pkmn/engine

对外接口

C ABI (pkmn.h) → 任意语言可绑定

设计原则

No compromises on performance 一切让位于性能

当前进度

Stage 1：Gen 1 (红蓝) ✓ · Gen 2 (金银) ✓ · 后续：Gen 3/4

明确不做

队伍校验 / mods / 三打四打 / 输入校验 / UI

三个最关键的设计决定：

  • 1 每个世代独立实现——不像 Showdown 那样"一份现代代码 + mods"。代价是代码重复，好处是每代都极简极快。
  • 2 静态数据由代码生成——tools/generate 生成 data/moves.zig，运行时直接数组下标访问，0 hash 查找。
  • 3 无字符串 / 无动态分配 / 无指针——所有 ID 都是 1 字节 enum，所有引用都是数组下标 ("handle"）。

③ 引擎中的核心抽象与实体

3.1 数据实体（"名词"）

整场战斗的全部状态总共 384 字节——可以直接 memcpy 存档/读档/并行复制。

Battle 384 B

一场战斗的全部状态：两个 Side + 回合数 + RNG 状态 + 上一次伤害值。

Side 184 B

一方训练家：6 只 Pokemon + 出场 ActivePokemon + 顺序 + 上一招。

Pokemon 24 B

未出场态：原始能力值、4 个 MoveSlot、HP、Status、种族、类型、等级。

ActivePokemon 32 B

出场中态：修改后能力值、当前种族（变身用）、当前类型、能力等级、Volatiles、招式槽。

MoveSlot 2 B

{ 招式 ID, 剩余 PP }，每只宝可梦 4 个。

Volatiles 位字段

临时状态：混乱 / 束缚 / 替身 / 屯能 / 变身 / 麻痹回合数 / Toxic 计数...

Status 1 B

主状态 enum：SLP / PSN / BRN / FRZ / PAR

Choice 1 B

玩家指令：{type, data}，type ∈ {Pass, Move, Switch}

Result 1 B

update 返回：胜/负/平/继续 + 下一步可选指令类型。

ID 1 B

场上某只宝可梦的引用：{player, slot} 压成 8 位。

关键： Pokemon 和 ActivePokemon 是两个不同的结构。"存档态"和"战斗态"分开存，让最热的字段紧凑放在一起，最大化 CPU cache 命中率。

3.2 静态数据（"图鉴"，每个世代的不变规则）

静态数据文件形态
Move enum + Move.Datagen1/data/moves.zig165 个枚举 + 同长度的 4 字节数据数组 {effect, bp, accuracy, type, target}
Species + Statsgen1/data/species.zig151 只宝可梦的基础种族值、类型
Type + 相克表gen1/data/types.zig15 种属性 + 相克矩阵
Item（Gen 2 起）gen2/data/items.zig持有道具枚举（薄荷、莓果、Leftovers…）

3.3 行为抽象（"动词"，全在 mechanics.zig）

抽象函数作用
入口update(c1, c2)整个引擎唯一对外动作：吃两边指令，前进一回合
入口choices(player, result)给定当前 result，列出该玩家能选的所有合法指令
内部turnOrder比较速度+优先度，决定本回合谁先动
内部executeMove一方完整出招的流水线入口
内部beforeMove麻痹/睡眠/冰冻/混乱/退缩判定
内部calcDamage / adjustDamage / randomizeDamage三段式伤害计算
内部checkHit / moveHit命中判定
内部applyDamage扣 HP / 处理替身吸收
★moveEffect + Effects.*招式副作用的 dispatch 与实现（详见 §4）
内部handleResidual回合末：中毒/烧伤/Leech Seed 残留伤害
内部endTurn收尾：检查胜负 → 写日志 → 返回 Result

3.4 跨切面抽象（可选编译模块）

模块编译开关作用
PRNG—抽象 RNG。默认卡带 RNG；-Dshowdown 切到 Showdown RNG；测试用 FixedRNG 强制指定每次掷骰
Log / Protocol-Dlog可选的二进制日志输出。关闭时整条日志代码被编译器消除
Chance-Dchance记录本次 update 发生了哪些 RNG 事件，供 AI 重放/搜索
Calc-Dcalc允许覆写伤害结果，做伤害计算器

这四个模块都用 Null Object Pattern——没启用时占 0 字节，所有调用编译期消除。

④ 招式 / 道具 / 特性的"效果"是怎么实现的？

这是最关键的设计点。引擎采用 "枚举 + dispatch" 模式，而不是 OOP 的"每个招式一个 class"。

4.1 招式的数据结构

每个招式就是一行 4 字节静态数据，没有任何代码：

// gen1/data/moves.zig
pub const Data = packed struct(u32) {
    effect: Effect,     // 1 字节：副作用类别
    bp: u8,             // 威力
    accuracy: u8,       // 命中
    type: Type,         // 属性
    target: Target,     // 目标
};

// 示例：火焰喷射
.{ .effect = .BurnChance1, .bp = 95, .type = .Fire,
   .accuracy = percent(100), .target = .Other },

很多招式共用同一个 effect——"火焰喷射 / 火花 / 喷射火焰" 都是 .BurnChance1，只是威力/命中不同。这就极大地压缩了代码量。

4.2 effect 是怎么被触发的？

Effect 枚举的顺序是有意安排的——前 16 个是 onBegin 类、17–31 是 onEnd 类，依此类推。这样可以用整数比较快速分类：

pub fn onBegin(effect: Effect) bool {
    return @intFromEnum(effect) > 0 and @intFromEnum(effect) <= 16;
}

在主流水线的对应节点，做一次大 switch 分发：

fn moveEffect(battle, player, move, options) !void {
    return switch (move.effect) {
        .BurnChance1, .BurnChance2  => Effects.burnChance(...),
        .ConfusionChance            => Effects.confusion(...),
        .FlinchChance1, .FlinchChance2 => Effects.flinchChance(...),
        .FreezeChance               => Effects.freezeChance(...),
        .HyperBeam                  => Effects.hyperBeam(...),
        .ParalyzeChance1, .ParalyzeChance2 => Effects.paralyzeChance(...),
        .PoisonChance1, .PoisonChance2 => Effects.poison(...),
        .AttackDownChance, .DefenseDownChance, .SpecialDownChance,
        .SpeedDownChance            => Effects.unboost(...),
        else => {},
    };
}

Effects 是一个纯函数命名空间（pub const Effects = struct { fn burnChance(...){} ... }），每种效果一个函数，直接操纵 battle/side/active.volatiles 等字段。

4.3 道具与特性

  • 道具：Gen 2 起 Pokemon 多了 item: Item 字段，1 字节 enum。在 gen2/mechanics.zig 的不同时机以同样的 switch dispatch 生效（Quick Claw 优先度、Leftovers 回血、Berry 解状态、King's Rock 退缩…）。
  • 特性：Gen 1/2 没有此概念。但未来引入时也会是同样模式：1 字节 Ability enum + 各事件钩子点 switch dispatch。

4.4 与 Pokémon Showdown 对比

Pokémon Showdown（事件系统）

每个招式 = 一个 JS 对象，带 onTryHit, onModifyMove, secondary 等回调钩子。

派发方式：事件冒泡，遍历招式/精灵/场地/道具/特性查找处理器。

扩展性极强 几小时就能加新世代；性能慢

pkmn/engine（switch dispatch）

每个招式 = 一行 4 字节数据 + 一个 Effect enum 标签。

派发方式：固定流水线节点上做一次 switch，编译成跳转表。

扩展性极弱 每个世代都要手写；性能极快

⑤ 整个引擎是怎么"跑"起来的？

无论用什么语言写驱动，调用模式永远是同一个循环：

① 构造 Battle
填入两队精灵、招式、HP、PRNG seed
↓
② 首次 update(Pass, Pass)
触发"派出第一只"
↓
③ result = update(c1, c2)
推进一回合
④ choices(P1, result.p1)
列出 P1 合法指令
⑤ choices(P2, result.p2)
列出 P2 合法指令
↓
⑥ AI/玩家从合法列表里挑指令 → 回到 ③
↓
⑦ result.type ≠ None → 退出
判 Win / Lose / Tie

整个 API 就 2 个函数：update + choices。Battle 整体是 384 字节连续内存——存档/读档/并行 MC 搜索都是直接 memcpy。

💥 示例 C — 触发"屯能(Bide)"：一个多回合持续效果

这个例子最能展示 Volatiles 位字段 + Effects 函数 + 主流程检查 三者如何形成一个"小型状态机"。

时机层级做了什么
第 N 回合 首次使用 Bide Effects.bide 设置 volatiles.Bide = true、volatiles.state = 0（累计伤害）、volatiles.attacks = 2 或 3（持续回合，PRNG 决定）
同上 options.chance.observe(.attacking, ...) 记录"抽到 2 还是 3"——供 AI 搜索重放
第 N+1 / N+2 回合 selectMove 主流程 检测到 volatiles.Bide == true → 不让玩家选指令，强制重复 Bide
被打中时 applyDamage 累加进 volatiles.state
volatiles.attacks 减到 0 doMove 释放分支 把累计伤害 ×2 砸向对面，清空 Bide 状态

⑦ 如何为洛克王国类游戏做一个类似引擎？

如果你想给一款国产 PKM 风格对战游戏（洛克王国、赛尔号、口袋妖怪 GO...）做一个 pkmn/engine 级别的高性能对战内核，按下面 7 步走：

步骤 0：明确"游戏战斗规则"边界

写一份规则文档，详细列出：战斗格式（1v1?2v2?）、指令系统、属性相克、能力值公式、招式属性（物理/法术/变化、PP、目标、优先度、特效）、状态系统、特性/个性、道具/法宝、场地/天气/五行/缘分、RNG 在哪里发生……规则冻结后再设计数据结构。pkmn/engine 能这么小这么快的根本原因，就是它实现的是完全冻结的、不再变化的规则集合。

步骤 1：定义"最小完备"的状态结构

参照 gen1/data.zig 定义你的：Battle / Side / Pet / ActivePet / SkillSlot / Volatiles / Choice / Result。 设计原则：① 全部状态打包成一个定长结构（可 memcpy）；② 不用指针，用整数下标当 handle；③ 不用字符串，所有 ID 是 enum；④ 冷数据/热数据分离；⑤ 不动态分配，所有缓冲区常量化。

步骤 2：把"图鉴"做成代码生成的静态数据

用 Python/Node 写脚本，从 JSON/Excel/服务器导表读取精灵/技能/道具表，生成目标语言源代码（Zig 的 [_]Data{}、Rust 的 static、C 的 const 数组）。关键：精灵和技能 ID = 数组下标，O(1) 查表，没有 hashmap。

步骤 3：实现主流水线

参照 gen1/mechanics.zig 的骨架：

update(c1, c2)
  ├─ selectMove(P1, c1)        ← 强制连续招处理
  ├─ selectMove(P2, c2)
  ├─ turnOrder(...)             ← 速度 + 优先度
  └─ doTurn(first, second)
        ├─ executeMove(first)
        │     ├─ beforeMove        ← 麻痹/睡眠/混乱
        │     ├─ canMove           ← PP / Disable
        │     └─ doMove
        │           ├─ checkHit
        │           ├─ calcDamage
        │           ├─ adjustDamage   ← 相性 + STAB
        │           ├─ randomizeDamage
        │           ├─ applyDamage
        │           └─ moveEffect     ← ★ 副作用 dispatch
        ├─ checkFaint
        ├─ executeMove(second)
        ├─ handleResidual          ← 中毒/烧伤/Leech 末伤
        └─ endTurn                 ← 写日志 + 返回 Result

步骤 4：实现"技能效果 / 道具效果 / 特性"

给每种效果类别定义一个 Effect enum 值（不是每个具体技能！多个相似技能共用同一个 effect）。在 Effects 命名空间里给每种 effect 写一个函数，直接操纵 Battle 状态。在主流水线的合适节点（onBegin / onHit / onEnd / onResidual）做 switch (effect) 分发。

如果你的游戏有"特性 / 缘分 / 五行"等会影响多种事件的机制，有两种选择：

  • A 像 pkmn/engine 一样硬编码：每个事件点 switch 里加 if-特性 → 快但代码丑
  • B 像 Showdown 一样建事件总线：可扩展、可玩家 mod，但慢

取决于目标：服务器实时对战、AI 训练 → A；玩家可自定义 → B。

步骤 5：RNG / 日志 / 测试

RNG 抽象：实现一个 FixedRNG，可强制指定每次抽签结果——单元测试和 AI 重放的基石。 二进制 protocol：定义一套字节码（|switch| / |move| / |damage|...）作为可选编译开关。 集成测试：跑大量 fixture 战斗，对比"参考实现"（你的服务器现有代码）的逐回合输出。 基准测试：用 zig build benchmark 这样的工具持续监控性能回归。

步骤 6：对外绑定

C ABI：导出 luoke_battle_update 这样的 C 函数；不暴露内部结构，只暴露不透明 handle。 Node / WASM：用 N-API 或 WebAssembly 包一层。 驱动层：用 TypeScript/Python 实现易用的高层 API（自动初始化、打印协议、AI 玩家接口）。

📌 TL;DR 一句话总结

  1. pkmn/engine ≠ 完整游戏，它是一个为极致性能而生的"对战内核库"。
  2. 每个世代独立硬编码，不抽象成"通用引擎 + 数据"。
  3. 核心实体只有 5 个：Battle / Side / Pokemon / ActivePokemon / MoveSlot，加上位字段 Volatiles / Status。
  4. 招式没有自己的代码，只有 4 字节数据 + 一个 Effect enum 标签，由 mechanics.zig 的大 switch 分发到 Effects.xxx 函数。
  5. 道具同理（Gen 2 起），未来的特性会以同样的模式加进去。
  6. 整个 API 就一对函数：update(c1, c2) → Result 和 choices(player, result) → [Choice]。
  7. 二进制 / 无字符串 / 无分配 / 无指针，是它比 Pokémon Showdown 快 1000 倍的根本原因。
  8. 想做洛克王国版本：先冻结规则 → 设计紧凑结构体 → 代码生成图鉴 → 实现固定流水线 → 用 enum + switch 实现效果 → 加 RNG 抽象与日志协议 → C ABI 暴露给上层。
